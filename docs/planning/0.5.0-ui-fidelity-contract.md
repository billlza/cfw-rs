# 0.5 UI fidelity contract — user correction, 2026-09-22

The user rejected the new Overview layout. The goal is the existing **0.4.0 UI
and interactions, with native SwiftUI/Liquid Glass component treatment**. This
explicit correction supersedes the earlier Overview-led interface direction.
Keeping backend commands while changing their screens, positions and interaction
paths is not functional/UI parity.

The visual/behavioral reference is build 40073 at source
`9e2f76cdd7ffb286614a7bc6fe55e75d3fc7a5b2`. Its installed General page was inspected
without operating network controls. Its page inventory, General layout, HTML and window configuration remain the reference
for the 0.5 worktree. In-place native adapters and the explicitly measured component
differences below preserve that structure. The original reference hashes and measured geometry are in the companion
[contract JSON](0.5.0-ui-fidelity-contract.json). This is preservation of the old
frontend, **not evidence that a faithful SwiftUI replacement has been completed**.

## Preserve the product the user knows

- Nine pages in the same order: General, Proxies, Profiles, Providers, Logs,
  Connections, Rules, Settings, Feedback. Preserve names and all four translations.
- Keep the 170 px sidebar, upload/download readings, existing navigation selection,
  uptime/connection footer, branding and the content area's current density.
- Preserve General's exact row order: Port, Allow LAN, Log Level, IPv6 DNS, Engine,
  TUN MTU, Home Directory, GeoIP Database, TUN Mode, Mixin, System Proxy,
  Start with macOS. Keep inline icons, values, tooltips and action locations.
- Engine Start/Stop stays an inline text action. TUN and System Proxy remain their
  original row switches. Preserve Retry, Approve and Cancel request conditions,
  disabled reasons and pending/error behavior. Mixin remains explicitly unavailable.
- Preserve every page's existing menus, editing/import/export dialogs, filtering,
  sorting, selection, shortcuts, confirmation steps and persisted choices. No
  hidden replacement of a page with an inspector or an added intermediate step.
- Preserve the Rust coordinator, service permissions and network effects. A
  material/appearance change cannot restart networking or choose a different node.

The geometry values are reference measurements, not permission to override system
accessibility behavior or private control internals. Native-component differences
must stay within the original component's role and content footprint, be recorded
in the comparison, and never cause silent reflow or loss of an existing control.

## Concrete interaction references

The existing Profiles context menu is an appropriate first material migration:
it already has a glass-styled surface, so native material can replace that
surface without inventing a new workflow. Preserve this exact order and its
conditional visibility: Select, Edit, Edit externally, Update, Show in folder,
Edit outbounds section, Edit route section, Copy, QRCode, Credentials, Settings,
Delete. Keep remote-only disabled reasons, engine-Off requirements, deletion
confirmation, outside-click/Escape dismissal and the original right-click entry.
Do not turn the menu into a new inspector or move its actions to another page.

The existing Network settings dialog retains its Port and TUN MTU entry points
and field sequence: port, log level, MTU, IPv6 DNS, LAN sharing, LAN listener,
LAN port, trusted source ranges, Cancel/Apply. Enabling LAN opens this dialog
before exposing a listener. Saving blocks dismissal; failures retain the draft
and error. Proxies keeps Global → Rule → Direct, the current node grid and group
rail, with the same manual/automatic selection and delay-test behavior.

## Change only the component treatment

Use native SwiftUI controls/materials at the existing locations. Retain the current
content hierarchy, labels, icon meaning, state colors/meaning, density and action
sequence. No new full-width hero, large status cards, extra top action strip,
combined pages, favorites or inspector workflow is authorized by this UI refresh.

Apple treats Liquid Glass as a controls/navigation material; standard components
supply its behavior. Choose appropriate existing control or menu surfaces, keep
text/tables/logs legible, and respect accessibility settings. Prefer standard
button styles; group nearby custom glass effects when needed and limit simultaneous
effects. These are implementation constraints, not a reason to redesign the app.
Sources: [adoption](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass),
[custom views and performance](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views).

## Next implementation and acceptance

1. Capture each existing page and significant menu/dialog state at equal window
   size, locale, scale and engine state. Record action locations and sequences.
2. Replace one component family at its existing location, carrying over the same
   actual data and action binding. Unmigrated working areas remain available.
3. Compare the whole page and interaction sequence, not just the new component.
   Investigate any changed order, missing field, moved action or extra step.
4. Only then repeat for the next component family. Run appropriate integration,
   accessibility and measured performance checks. Rendering or disabled sample
   controls do not establish completeness or network acceptance.

The corrected UI is being implemented one component family at a time; full
installed fidelity is not established yet. No new installer is to be
presented as the requested 0.5 UI until this fidelity contract is actually met.

## In-place General switch implementation — 2026-09-25

General now has a third native component family in the development worktree: its
six existing switches (LAN, IPv6 DNS, TUN, Mixin, System Proxy, login startup).
The twelve rows, row labels, notes, icons, text actions and their business handlers
remain in the original renderer. SwiftUI presents standard system switches through
borrowed-WKWebView geometry; it never owns a network effect. The 90 original Rust
business commands are unchanged. Three presentation commands bring the total to 99
(the count on this date; the 2026-10-05 section below gives the current total).

The current macOS system mini switch measures 54×24 points, compared with the old
34×20 custom drawing. The six slots reserve that intrinsic size at the original
right edge, retaining the 35-point minimum row height and 10-point action spacing.
No scaling or clipping of a system control's internals is used. Standard switches
supply the platform's Liquid Glass interaction; no additional custom glass layer
is placed over content or logs.

Live WKWebView testing exposed and corrected initial-theme admission and focus
return after a native action/modal. Tab and Shift+Tab retain the DOM action order;
Space uses the same native intent path. Mixin remains unavailable, LAN enable
continues to open the existing settings form, and a rejected TUN command stays Off.
The original General content area clipped long error messages and its bottom rows.
It now scrolls only when needed; original normal-state density is unchanged. Tab
scrolls an offscreen target into view before native focus. The overlay clips to
the actual General content viewport, not the whole window.

These observations come from the explicit TEST DATA component host, not the
installed signed product. A subsequent real zoom-in/zoom-out run found an
asynchronous WebKit/native viewport race; the new stale-geometry response was
validated with three real zoom/restore cycles: six stale geometries were retained
as pending and followed by accepted current frames, with all six controls
remaining available and responding afterward. Full signed-host, VoiceOver, network and comparative
performance acceptance remain open. Do not describe these component results as
completion of all 0.5 requirements.

Native checked controls use the system accent appearance in place of the old custom thumb colors; their explicit On/Off values and unavailable reasons remain unchanged.

The General event channel is created once per successful native attachment; subsequent
frames carry no new channel owner. A rejected initial geometry uses a new callback
on retry. Current frontend tests exercise the actual Tauri JavaScript Channel end
and ordering behavior, and the Rust boundary uses its public deserializable channel
ID. The final isolated host retained input delivery through sixteen updates, page
changes and a resize, then ended the channel only on normal quit. This still needs
the separately signed production Host boundary check.


## In-place prompt dialog implementation — 2026-10-05

The development worktree has a fourth native component family: the three existing
dialogs that only ask or inform. They are profile deletion (No / Yes), Reset all
settings (No / Yes) and the information notice (Close). Every other dialog kind
(copy, profile information, credentials, DNS query, previews, About, legacy
migration) is still the original page dialog.

Preserved: the entry points (Profiles context menu › Delete, Settings › Reset, the
existing information actions and legacy-migration results), the catalog texts in
all four languages, cancel on the left and the action on the right, and the
confirmation step. A native Yes runs the same function as the page's Yes button,
so `delete_profile` or `reset_settings_snapshot` is invoked once and the same log
line is written. A refused action keeps the dialog open and reports in the log,
without an inline error, as before. No, Close, Escape and the dimmed page backdrop
dismiss at any time, also while a confirmed action is still running, as on the
page. Dismissing does not cancel that action, and its result closes only the
dialog that started it. No button answers Return. Opening a dialog issues only its
presentation command.

The page dialog is kept, unchanged, whenever the native panel cannot carry the
dialog exactly: a host without the component, a migration handoff that is
announced or in progress, a page theme that is not resolved yet, text that is not
well-formed UTF-16, and text beyond the bounded native frame (title and button
titles 160 and message 4096 Unicode scalars, 16,000 bytes encoded). A native
presentation the host refuses is never replaced by a confirmation. The page then
shows the dialog's title and text, the refusal with diagnostic secrets redacted,
and dismissal only, and the log names the dialog whose presentation failed.

Treated, with each value taken from the page dialog's own rules:

- Sheet (`.glass-dialog`, one translucent sheet with 16px corners): one Liquid
  Glass shape with 16-point corners on macOS 26 and later, the regular material
  with a half-point separator on macOS 15–25, and an opaque window background when
  Reduce Transparency or Increase Contrast is on (a 1-point separator with
  Increase Contrast).
- Buttons (`.glass-btn`, solid pills at 13px/600 with `padding: 7px 14px`; blue,
  grey for `.ghost`, red for `.danger`): solid system capsules, so no control
  stacks glass on the glass sheet. Cancel is the bordered grey capsule. The action
  is filled with the page's blue `rgba(0, 122, 255, 0.95)` and the destructive
  action with the page's red `rgba(255, 69, 58, 0.95)`. All are 13 points semibold.
- Text: the title is 15 points semibold with -0.3 tracking. The message is 13
  points medium at the page's 1.45 line height, in the label colour at 0.9
  opacity, which is close to the page's `#3a3a3c` on its light sheet.
- Layout: `min(360px, 100vw - 32px)` wide and centered in the content area, with
  the page's 18/18/14 padding and half-pixel border, 12 between blocks, and the
  buttons 8 apart and 4 below the block gap.

The Network settings panel now uses the same sheet and the same buttons, so the
two native dialogs are visibly one family. For that panel this changes exactly
two things. On macOS 26 and later its regular-material sheet with a half-point
separator becomes the Liquid Glass sheet; on older systems and with the two
accessibility settings its sheet is as before. On every system its Cancel and
Apply buttons, which were glass or bordered at the regular size, become the solid
capsules above at the large size, with Apply in the page's blue. On the test host
that is 28 instead of 24 points high, so the form is 4 points taller where the
window leaves room. Its fields, texts, order, draft, submission and cancel rules
are unchanged. Its notes also stay as they were, in the secondary label colour at
the system line height: the page colour and 1.45 line height of
`.glass-dialog-copy` were applied to the prompt only.

Measured in the unit-test host on macOS 27.0 in the light appearance. At the five
system control sizes, mini to extra large, this button is 18, 22, 24, 28 and 36
points high with 8, 10, 12, 14 and 18 points beside its label. The page pill is
`padding: 7px 14px` around one line of 13px text, about 30px high. The large size
is therefore used: its 28 points are the nearest a system control comes to the
page's height, and its 14 points beside the label are the page's value. No is 46
points wide, Yes 51 and Close 64. A 13-point line measures 16 points and a
15-point line 19; the message lines are 18.85 points apart, which is 13 × 1.45.
The English delete dialog in an 850×603 content area is a 360×146 panel, centered
horizontally and half a point below the vertical center because AppKit places
windows on whole points. Adding up the stylesheet values with those two line
heights gives 147.7px for the page dialog, so the native panel differs from it by
the 2 points of the button height. The page dialog itself was not rendered and
measured in this change, and no screenshot of either was compared.

Remaining differences from the page dialog, each with its reason:

- Theme. The page dialog has no dark rule and is always a light sheet. The native
  panel follows the page theme, as the Network settings panel does, because a
  system material and system controls take their appearance from it.
- Button height. 28 points instead of about 30px: the nearest size a system
  control has.
- Page shortcuts. While the panel is the key window, key presses go to it, so the
  page's own shortcuts (Command-1 to Command-6 for the pages and the single-letter
  mode, system proxy, TUN and save shortcuts) do nothing until the dialog is
  closed or the main window is clicked. The page dialog left them active
  underneath it. Menu commands are unaffected.
- Tall text. A message taller than the content area less 32 points scrolls inside
  the panel, so the buttons stay reachable. The page dialog had no height bound.
- Line breaks. A line break in a notice is shown as a line break. The page
  collapsed it into a space.
- Accessible name. The panel is named by its visible title. The page dialogs for
  Reset all settings and for notices carried the fixed names "Reset settings" and
  "Info" beside a different visible title.
- Tab. Tab stays among the panel's buttons and reaches them only with the system
  Keyboard navigation setting. On the page, Tab continued into the page behind
  the dialog. The setting was off on the test machine, so traversal was not
  exercised.

Corrected in the hosting type the two native dialogs share: a panel that was
hidden with its window, by hiding or minimizing, was shown again without being
attached to that window, so a click on the main window could cover the dialog. It
is attached again when it is shown again, and a test fails without that.

The Network settings panel and this panel share one hosting type, one sheet and
button treatment and one Rust session module. Apart from the look and the
re-attachment described above, the settings panel behaves as before. Its Swift
tests gained only a test of the activating panel policy from the 2026-09-27
dismissal fix, which the menu and this panel now have as well. Its two Rust
session tests kept their assertions and moved onto the helpers the two families
share.

Twelve presentation commands and one explicit startup recovery command now stand
beside the 90 unchanged business commands: 103 registered in total.

The in-app installation carried forward from the 0.4 line later on the same date
adds four update installation commands, 107 in total. Its only interface change
is in the About dialog, which stays a page dialog: beside Check for Update and
the download page it offers Install Update, Cancel and Install and Relaunch, as
the 0.4.0 release that contains the installer does. Its result notices use the
information prompt and therefore the native panel where that is enabled.

Evidence in the development worktree on this date: 215 frontend tests, 77 Swift
package tests, and the host tests with and without the component (474 and 459)
passed; the Swift build and Clippy treat warnings as errors. The page markup of
the three dialogs was pinned by a test before the renderer changed and is
byte-identical afterwards. The ownership rules of the session module are driven
through a test family whose panel is three Rust functions: a rejected
presentation, a panel that closes before its presentation returns, the reload
epoch, every native status, a close that carries a differing session, and that no
state lock is held across a call into the panel. New and changed tests were run
against deliberately broken implementations and failed. Two Swift tests are the
exception: the line-height test and the wrong-thread test for present and update
pass, but the one run that broke their implementations stopped before reaching
them.

Not validated on an installed signed build, and in need of eyes there: how the
Liquid Glass sheet and the solid capsules look over the WKWebView in both themes,
for this panel and for the Network settings panel; the macOS 15–25 material and
the reduced-transparency and increased-contrast surfaces, which compile but were
rendered in no test here; the activation hand-off from the native Profiles menu
to the delete panel; real mouse and keyboard input, including Escape and Tab;
focus returning to the WKWebView after dismissal; and the VoiceOver announcement
(dialog role and title, header, button labels and roles). The component
integration host does not present this family. These are unit and component
results, not acceptance of the 0.5 interface.


## Native window glass — 2026-10-06

The user rendered the look they want: the whole window is Liquid Glass over
the desktop, the sidebar and the content area are frosted panels on it, the
traffic and running-time cards and the selected navigation item are lighter
glass, and every page element (header with the cat mark, name and version, the
nine navigation items, the General rows, texts and order) is the one the page
already has. The slogan "Less Network / More Freedom" is set as plain rounded
text at the header's right, not as glass, as the user decided. The title bar is
hidden so the traffic lights sit on the glass; the status row stays, as the
drag region beside them, and the sidebar keeps both the running-time card and
the connection line.

This is the fifth family, `WindowGlass.swift` behind `cfm_window_glass.h`,
and the first that lies *under* the page instead of over it: it is inserted
below the WKWebView of the host window and takes no input. The window is
transparent (`transparent`, `titleBarStyle: Overlay`, `hiddenTitle` and
`macOSPrivateApi` for the transparent WebView — a private Apple KVC the user
accepted; Developer ID distribution is unaffected). The page measures seven
regions (`ui/src/window-glass.js`: status row, sidebar, traffic card, active
navigation item, running-time card, status card, workspace) in CSS pixels and
sends them with the viewport and appearance; the host converts them through
`WebContentGeometry` and refuses a frame whose viewport the view no longer has
(the resized page measures again). On macOS 26 and later the slab is
`glassEffect(.regular)` in a 28 pt continuous rounded rectangle and the
navigation pill `glassEffect(.regular.tint(blue))`; panels and cards are
white (light) or black (dark) fills at fixed opacities with a hairline, so no
two glass materials stack over a large area. Before macOS 26 the slab is the
system's behind-window material and the pill a tinted fill.

The page paints no background of its own only while `html.native-window-glass`
is set, which the renderer sets after the host accepted the backdrop and
removes when the host closes it or refuses a frame; without the class every
earlier rule applies, so a transparent window never shows an unreadable page.
In glass mode the navigation items show the product's own glyphs beside their
labels (`ui/src/nav-icons.js`), rows separate with hairlines, inputs, selects
and buttons are frosted capsules, and the colour tokens change to the deep
navy ink of the rendering. The General switches stay the native family they
were.

Verified on 2026-10-06 in the development worktree: an API check on this
macOS 27 machine showed that a transparent third-party window's
`glassEffect` does show the desktop and windows behind it; 5 Swift tests of
the family (frame strictness, order below the page, geometry conversion,
stale and refused frames, close ownership, wrong thread); 281 frontend tests
including 9 of the page's side; the host's unit tests with and without the
component. Not verified: the rendered result in a signed build on this
machine, the exact opacities against the rendering, the sidebar at the
smallest window size, and VoiceOver with the hidden title bar.

## General page refresh — 2026-10-05

Before this date, while the engine ran, every connections snapshot, about one a
second, re-rendered the whole General page when General was the page on screen.
General shows no connection data; only the status bar does. Now a snapshot
refreshes the status bar on every page and patches the Connections page when that
page is on screen, and General keeps its DOM between snapshots. The reason is the
native switches: replacing the page once a second detached the six switches, and
the page's own controls, from the elements a pointer or an assistive client was
about to use. The rows, labels, values and handlers of General are unchanged. A
frontend test counts the writes to the page across snapshots and fails on the old
behaviour.
